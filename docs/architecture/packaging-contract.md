# Kiyo Compass — Static native packaging contract

Decision date: **2026-09-29**. Selected design:
[ADR-001](decisions/ADR-001-static-canonical-packages.md). Requirements:
[REQ-002–007/026/027/053/054/059/064/067/076–079](../build/REQUIREMENTS.md).
This document originally selected the architecture. Prompt 20 implements the
[Claude development bundle](../compatibility/claude-package.md) and a bounded
developer packager. Prompt 21 adds the [Codex development bundle](../compatibility/codex-package.md);
Prompt 22 adds the [Copilot development bundle](../compatibility/copilot-package.md).
All live installations remain pending.

## Single authored source, self-contained derived resources

Author product instructions only under `src/kiyo/`. Overlays may select native
metadata and render native project-adapter text; they may not maintain alternate
core/workflow/template prose. Distributions are generated, never a second
editable specification. The developer packaging step is a build operation;
users receive ready-to-install static files and never run it.

For portability, select a **complete shared resource snapshot inside each skill**.
Copy `KIYO.md` and the product Markdown under `framework/`, `governance/`,
`agent-security/`, `workflows/`, `profiles/`, `templates/` to
`skills/<name>/references/kiyo/`, preserving the shared subtree layout. Do not
copy `skills/` recursively. Every skill thus owns a contained copy of the same
shared snapshot. Packaging duplicates generated bytes, not eight authored rulesets
or eight long SKILL.md bodies. Accept the modest package-size tradeoff; optimize
only with evidence and a later architecture decision.

Include the whole shared snapshot rather than introduce a runtime dependency
resolver or a complex first-version graph pruner. Installed size is separate
from loaded context: the agent still reads only relevant references. Shared
content must not depend on another skill's SKILL.md or a source checkout.

## Worked reference path

All names below are **planned examples**, not existing procedures or a tested
package. `review` is the selected internal skill slug, not a reserved marketplace
namespace. The same transform applies to all eight skills.

| Stage | Planned path / operation | Why it stays self-contained |
| --- | --- | --- |
| Canonical entry | `src/kiyo/skills/review/SKILL.md` references `../../KIYO.md` and `../../workflows/review.md` | One authored bootstrap and review procedure |
| Shared rule | `workflows/review.md` references `../framework/evidence.md` and stable Kiyo IDs | Long evidence rules are written once |
| Template | The procedure references `../templates/review-report.md` | Neutral template contains no developer project facts |
| Build transform | Rewrite skill-entry links to `./references/kiyo/KIYO.md` and `./references/kiyo/workflows/review.md` | Installed SKILL.md does not escape its directory |
| Shared snapshot | Copy shared files with their relative directory layout intact | `../framework/` and `../templates/` still resolve inside the same snapshot |
| Native root | `dist/<ecosystem>/skills/review/SKILL.md` plus `references/kiyo/` and native manifest | Host loads its native entry; the agent follows real installed relative paths |
| Consumer output | Authorized report in user-selected project location, or answer only in read-only mode | Output is mutable project state, never written into installed resources |

Illustrative payload (no files created here):

```text
<native-package-root>/
  <documented-native-manifest-location>
  LICENSE                         preserved legal material, subject to release gate
  skills/review/
    SKILL.md                      native frontmatter plus canonical entry/body
    references/kiyo/
      KIYO.md
      framework/...
      governance/...
      agent-security/...
      workflows/...
      profiles/...
      templates/...
  skills/<each-of-the-other-seven>/...  same complete shared snapshot
```

The eventual generator rewrites **local skill-entry reference destinations only**
and merges an allowlisted native metadata overlay. It preserves fragments and
shared-file bytes. Literal path instructions in prose must use the same declared
mapping; validators reject unresolved authoring paths. Do not use an unrestricted
search/replace across prose, control IDs or external URLs. Prefer ordinary
relative Markdown links for operational resources; optional citations cannot be
prerequisites for following the installed workflow.

Template usage guidance stays in the installed resource. The artifact body copied
into a consumer project must not carry payload-relative operational links with it:
use stable control IDs and evidence paths relative to the actual project output,
or explicitly identified external citations. Resolve user-specific values from
authorized project evidence and keep unknowns labeled. A generated report or
memory entry must remain readable after plugin uninstall without a cache path.

No runtime placeholder substitution or author-machine environment variable is
needed. Resolve from the actual SKILL.md/shared file supplied by the host, never
the shell's current directory. Directory movement leaves the relative relationships
unchanged as a design property; actual host resource reads remain NOT_TESTED.

## Overlay contract and six-target boundary

The following candidates are based on the
[Prompt 02 capability matrix](../compatibility/platform-capabilities.md) and
[source register](../research/SOURCES.md), checked **2026-09-28**. They remain
DOCUMENTED_ONLY, with no P03 live or schema validation. Revalidate exact schemas
and required fields in the native implementation prompts before producing a manifest.

| Overlay / target | Candidate native output | Limit or gate retained |
| --- | --- | --- |
| Claude / CLI | `.claude-plugin/plugin.json`, `skills/` | Claude-specific documented schema; no assumed Agent Plugins 1.0 support (C01/C04/C07) |
| Claude / VS Code | Same candidate bundle, separate adapter/test record | Shared engine is documentation, not tested parity (C05) |
| Codex / CLI | Agent Plugins 1.0 root `plugin.json`, `skills/`; native-only additions only when justified | Do not combine legacy `.codex-plugin` and portable schemas blindly; exact selector/custom lifecycle remains unresolved (O01/O02/O04/A01) |
| Codex / IDE | No native plugin output selected | UNSUPPORTED in research; DEC-004 requires owner decision before any standalone fallback is accepted (O04/O05) |
| Copilot / CLI | Agent Plugins 1.0 root `plugin.json`, `skills/` | Custom/native marketplace metadata separate; no invented project-scope flag or Markdown PLUGIN_ROOT expansion (G01/G02/G03/A01) |
| Copilot / VS Code | Same portable candidate if validated; explicit VS Code metadata differences in overlay | Independent syntax/harness/enablement tests; plugin rules are not an established core loader (V01/V02/A01) |

Three ecosystem directories do not collapse six verification targets. If CLI and
IDE metadata diverge, keep the host-specific overlay parts in that ecosystem;
derive separate outputs only when necessary. Do not fork canonical Markdown to
mask an unsupported capability. Curated listing and custom-source registration
remain distinct native distribution choices, not a Kiyo installer or evidence
of public marketplace acceptance; see the [native route map](../compatibility/native-invocation-map.md).

Canonical frontmatter has `name` and `description` only. Host-specific fields
(for example invocation controls or a separate native metadata file) belong to
overlays, with source, check date, target and reason. Keep Kiyo read/write/execute
contracts, governance levels, approval requirements and control IDs in Markdown.
Do not invent `kiyo-permissions`, `core`, `rules` or another field in a closed
native schema. Copilot rules semantics remain UNKNOWN for bootstrap purposes;
this architecture does not need that optional component.

There are no MCP, hook, LSP, script, executable or network-service components,
including empty optional configurations. Native host software is a prerequisite;
a Kiyo consumer runtime is not. Tools run by the host during an authorized user
task are not bundled Kiyo software or permission grants.

## Payload boundary and provenance checks

Future packaging must fail, rather than silently omit content, on any of these:

- Missing bootstrap/reference/template, unresolved anchor, case mismatch, duplicate
  native skill identity or references outside the packaged resource boundary.
- Absolute developer paths, file URIs, hardcoded cache directories, home shortcuts,
  external symlinks/junctions/reparse points, or path traversal outside the skill's
  resource snapshot. Reject symlinks entirely in the initial package design.
- Links from operational content to `docs/`, `tools/`, `tests/`, source README,
  `.git/`, another checkout or developer evidence required at runtime.
- A developer tool/dependency, research fixture, populated `.kiyo` store, secrets,
  project-specific template values or prohibited runtime component in the payload.
- A schema field not established by that target's checked contract, or a native
  permission implication unsupported by evidence.

The build writes a developer evidence inventory outside the payload under
`docs/evidence/packaging/` (planned): source revision, canonical paths, source and
output digests, explicit link/metadata transforms, overlay inputs, tool environment,
target and actual check results. Generated shared copies must be byte-identical
to their canonical originals. Rendered skills must match canonical content after
only the recorded link/metadata transforms. Hash evidence is not a signature,
certification, provenance guarantee or proof of behavior.

Only allowlisted product files, required native static metadata and applicable
legal files enter a release. Preserve the existing LICENSE; final license,
publisher and release identity are still [owner decisions](../build/DECISIONS.md).
No default publisher, release version or signing identity is manufactured.

## Verification gates and lifecycle

| Layer | Future acceptance evidence | Current state |
| --- | --- | --- |
| Static package validation | Native schema; exactly eight entries; complete relative references; standalone copy; normalized body/control parity; neutral templates; two builds with identical inputs and equal artifact digests | Claude offline checks PASS in [P20 evidence](../evidence/claude/package-checks.md); Codex selected-field/closure checks PASS in [P21 evidence](../evidence/codex/package-checks.md), ingestion FAIL for owner fields; native loading pending |
| Behavioral evaluation | Agent follows bootstrap then selected procedure; uses relevant template; preserves permissions, project policy, read-only effects and existing memory location | NOT_RUN |
| Six independent live tests | Observed host/OS/account-policy scope; install, discover, invoke, implicit selection, relocated/cache resource reads, update, disable and uninstall | NOT_TESTED for every target; unsupported IDE route stays explicit |

Developer tools may later require a development interpreter, but that interpreter
and generator are excluded from native payloads and user installation steps.
No install-time build is allowed. Native source installs must point at a prepared
bundle containing final resources, not an unbuilt `src/kiyo/` directory.

Use native lifecycle mechanisms and scope documented for the actual target.
Plugin updates replace generated immutable content; they do not modify project
policy/memory or automatically refresh the project block. Uninstall must not
delete that user state. Adapter maintenance follows
[content-loading](content-loading.md#adapter-ownership-and-lifecycle). Exact native
cache/update behavior and relocation remain evidence gates, not assumed facts.

## Prompt 20 implemented transform

[tools/package_claude.py](../../tools/package_claude.py) generates dist/claude from
105 canonical product files, one Claude activation overlay and native manifest,
plus root LICENSE. Each of eight skills gets 97 unchanged shared resources.
Entry bodies differ only by local reference destinations, LF normalization and
a conditional link to the packaged Claude adapter; canonical skills remain unchanged.
The adapter's source ../kiyo references are validated at their rendered
references/claude location. No operational link requires the developer tree.

The native manifest contains name/description only. The owner-incomplete
marketplace template stays outside the plugin. Source/output hashes and actual
base revision are in [the Claude inventory](../evidence/claude/package-inventory.json);
the generator's own digest/environment and tests are in
[package checks](../evidence/claude/package-checks.md).
Identical output is a no-op; different pre-existing output is rejected without
overwrite/deletion. This bounded builder is not a generalized cross-platform
release engine or a consumer installation dependency.

## Prompt 21 implemented Codex transform

[Codex builder](../../tools/package_codex.py) reads the same 105 canonical product
files, a distinct portable OpenAI manifest/adapter and root LICENSE. It derives
the compatibility manifest from the portable input; it does not consume Claude
metadata. Existing developer filesystem/hash helpers are reused unchanged.
dist/codex/kiyo-compass is the plugin root; its outer name matches the working ID.

The generated entry/remapping/shared-snapshot contract is unchanged. Only the
conditional native adapter differs by target. Both manifests carry truthful
documented fields, no runtime components; optional agents/openai.yaml is omitted.
Source/output/tooling hashes remain outside the payload. No IDE fallback or
consumer build dependency is introduced.

Portable selected-field validation and stricter ingestion are distinct:
the latter FAILs for missing owner release metadata. See [submission gates](../compatibility/codex-submission.md).
This artifact is DEVELOPMENT_UNRELEASED, not proof of native acceptance,
public listing or cross-target parity. The earlier Claude output remains intact.

## Prompt 22 implemented Copilot transform

[Copilot builder](../../tools/package_copilot.py) independently reads the authored
three-field Agent Plugins 1.0.0 manifest and a shared CLI/VS Code adapter.
Current primary sources justify that manifest intersection; no compatibility
manifest, client extension, native permission field or VSIX is necessary.

dist/copilot/kiyo-compass contains eight entries with unchanged canonical shared
snapshots. Source/resource resolution uses the same recorded transform as the
earlier artifacts, with its own native reference. Existing filesystem/hash
helpers are reused; Claude/Codex manifests and generated outputs are not inputs.
[Offline evidence](../evidence/copilot/package-checks.md) records actual closure,
parity, no-op/relocation and rejection checks. No end-user build or runtime exists.

Owner-incomplete catalogs/settings are not generated. Final identity/version/
publisher/source remain release gates; both native Copilot targets are NOT_TESTED.
The common format does not make rules/hooks/commands or instruction semantics
portable. Later packaging/parity work remains Prompt 23, not silently completed here.
